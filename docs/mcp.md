# PushDocs MCP

PushDocs предоставляет remote MCP endpoint на адресе установки:

```text
https://docs.example.com/mcp
```

MCP работает через Streamable HTTP и OAuth Authorization Code с PKCE S256.
Git credentials остаются в PushDocs. Статические API keys не используются.

## Подготовка установки

Установите зависимости, выполните `yarn db:migrate` и перезапустите web и worker.
Установите `PUSHDOCS_PUBLIC_ORIGIN` в точный HTTPS origin установки.
Для разработки допускается HTTP на localhost.

Откройте Settings → MCP, чтобы увидеть endpoint и отозвать OAuth grants.
При подключении выберите проекты и разрешения. Доступ ограничен вашей текущей
ролью в каждом проекте. Grant действует не более 30 дней.

## Codex

```sh
codex mcp add pushdocs --url https://docs.example.com/mcp
```

Пройдите OAuth стандартным способом клиента. Не копируйте access tokens вручную.

## Claude Code

```sh
claude mcp add --transport http pushdocs https://docs.example.com/mcp
claude mcp login pushdocs
```

Авторизацию можно также открыть через `/mcp` в Claude Code. Войдите в PushDocs,
вернитесь к подключению при необходимости и выберите проекты на consent screen.

Сервер использует SDK 1.29.0 и поддерживает handshake MCP 2025-11-25.
Поддержка протокола 2026-07-28 не заявляется. Совместимость установленных версий
Codex и Claude Code требуется проверить перед выпуском.

## Примеры запросов

- Найди статьи про интеграции.
- Какие статьи ссылаются на docs/api/auth.md?
- Создай отдельную ветку, исправь статью и покажи изменения.
- Создай статью по шаблону, добавь её в sidebar после Webhooks.
- Проверь русскую и английскую орфографию, затем примени выбранные исправления.
- Покажи изображения статьи и оптимизируй выбранные файлы.
- Дай preview. Изменения пока не отправляй.
- Отправь просмотренный набор изменений и создай MR.
- Обнови все открытые MR с целевой веткой stable и отправь результат в их ветки.
- Объясни конфликты в MR и предложи итоговый текст.
- Покажи подробный анализ конфликтов с самими изменениями.
- Примени согласованные решения конфликтов и отправь результат в ветку MR.

## Черновики и конфликты

Change set общий для всех пользователей ветки. MCP видит сохранённые черновики,
включая правки других пользователей. Создавайте отдельную ветку для задачи.
Новая ветка получает Git snapshot, а не черновики исходной ветки.

`get_branch_changes` показывает Git diff. `get_change_set` показывает ещё не
отправленные документы и assets. Просмотрите весь change set перед submission.

Для обновления передавайте `revisionToken` из `get_document` и текущий
`changeSetRevision` как `expectedRevision`. При `REVISION_CONFLICT` перечитайте
состояние и примените изменения к новой версии.

Каждый write call требует новый `idempotencyKey`. При потере ответа повторите
тот же ключ с теми же параметрами. Для новой операции используйте новый ключ.
Branch creation и submission возвращают operation ID. Опросите
`get_operation_status`, прежде чем переходить к зависимому действию.

## Открытые PR/MR и обновление веток

`list_open_reviews` читает живой список открытых PR/MR у провайдера. Фильтры
`targetBranch` и `sourceBranch` точные, результаты имеют `cursor`/`limit`.
Для запроса «обнови все от stable» агент читает все страницы с
`targetBranch: "stable"`, обрабатывает каждую пару исходной и целевой веток
один раз и вызывает `update_review_branch` отдельно для каждой ветки. Это не
обход `list_branches`: закрытые, влитые и не связанные с открытым PR/MR ветки
в эту выборку не входят. Целевая ветка не подменяется основной веткой проекта.

`update_review_branch` принимает `reviewId`, `targetBranch`, `expectedHeadSha`
из списка и `idempotencyKey`. Требуется `pushdocs:submit` и право отправки ветки.
Операция сразу отправляет результат в исходную ветку, существующий PR/MR остаётся
открытым. Новый PR/MR не создаётся. Git определяет актуальность по истории:
готовность PR/MR, черновик и ожидание согласования сами по себе не означают, что
обновление не нужно. Статус определяет необходимость обновления, а способ выбирается
по настройкам репозитория с переопределением `git.updateStrategy` из конфига целевой
ветки. Выбранная политика сохраняется в операции и перепроверяется перед отправкой;
неизвестная политика блокирует запись. Настройки принятия PR/MR и squash не меняются.

Агент опрашивает `get_operation_status` для каждого задания и продолжает остальные
ветки при отдельной ошибке. Только завершённое задание сообщает `updateOutcome`:
`updated` или `already_current`. Подготовленный, но ещё не подтверждённый push
не считается успехом. Итоговая сводка разделяет обновлённые, уже актуальные,
конфликтующие и остальные неуспешные PR/MR и содержит ссылки на них.

Перед публикацией повторно проверяются OAuth grant, права, открытое состояние
PR/MR, обе ветки и исходные SHA. Форки, защищённые исходные ветки и исходная
основная ветка не поддерживаются. Сохранённые черновики и незавершённые загрузки
блокируют обновление; локальные несохранённые правки браузера MCP не видит.

Для такой ветки обновление или разрешение конфликтов возвращает `status: "blocked"`,
причину, пути файлов и ссылки на редактор и PR/MR. Задание не запускается.
Агент предлагает просмотреть общий change set и по отдельному явному запросу
закоммитить и отправить его; отменить выбранные ненужные правки в редакторе;
либо сохранить черновики и пропустить ветку, продолжив остальные MR.
При активной загрузке или операции сначала предлагается дождаться завершения.
Stash не предлагается. Команда массового обновления не разрешает автоматически
отправлять или отменять сохранённые правки. Проверка в транзакции очереди
остаётся обязательной; рекомендации не заменяют её и не мешают восстановлению
ранее подготовленного обновления.

После неопределённого push или ошибки синхронизации подготовленное обновление
сохраняется в том же задании. В новом чате вызовите `get_project` с `projectId`
и исходной `branch`: поле `pendingOperation` содержит ID, тип и статус операции,
которая удерживает ветку, включая задания закрытых и влитых PR/MR. Чтение ничего
не запускает. Если операции нет, поле равно `null`; `queued` и `running` нужно
наблюдать через `get_operation_status`.

При `canResumeReviewBranchUpdate: true` в `pendingOperation` или статусе задания
явный запрос пользователя продолжить обновление/отправку выполняется через
`resume_review_branch_update(projectId, operationId, idempotencyKey)`. Для новой
попытки нужен новый ключ; при потере ответа на сам resume повторяется тот же ключ.
Требуются `pushdocs:submit` и право отправки ветки. Возобновляется то же задание
с текущим OAuth grant, исходными SHA, стратегией и подготовленными коммитами.
Одновременные повторы не создают задания и не меняют авторизацию уже запущенной
операции. Счётчик попыток сохраняется; после исчерпания фоновых повторов следующая
неопределённая ошибка потребует нового явного resume.

Уже опубликованный результат синхронизируется без повторного push, даже если
PR/MR закрыт. Для неопубликованного результата сохраняются проверки открытого
PR/MR, обеих веток, политики и прав. Закрытый PR/MR приводит к отказу от публикации
и освобождению резервирования, журнал остаётся сохранённым. При удалённой исходной
ветке подтверждение прежнего push пока недоступно: resume не гарантирует завершения
и не пересоздаёт ветку. Этот механизм восстанавливает подготовленное обновление
или журнал прерванного rebase. После явного resume выделяется новый бюджет
технических повторов; монотонный номер lease сохраняется.

## Отчёт о конфликтах для редактора

`inspect_review_conflicts` требует только `pushdocs:read`, `reviewId` и
`idempotencyKey`. Это фоновый анализ без commit/push. После завершения
`operationId` передайте возвращённый `inspectionId` в `get_conflict_report`.

По умолчанию `mode: "editorial"`. Сервер возвращает проверяемые данные, а MCP-клиент
составляет ответ на языке пользователя в следующем формате:

1. Название статьи и раздела, ссылка на редактор и PR/MR.
2. Общая исходная версия и короткий фрагмент до расхождения.
3. Что изменилось в актуальной целевой ветке относительно исходной версии.
4. Что изменилось в ветке пользователя относительно той же исходной версии.
5. Предлагаемый итоговый текст, последствия выбора и конкретный вопрос, если
   смысл или выбор медиа неоднозначен.

Факты отделяются от предположений об авторах. Неизменившийся исходный текст нельзя
приписывать новой правке пользователя. Даты — committer dates общей исходной
версии и обоих проверенных коммитов, а не даты правки абзаца или вливания PR/MR.
Поиск исходного PR/MR для каждого изменения не выполняется. Даты не используются
для определения порядка коммитов. Если дата недоступна, она отсутствует в отчёте.

Ссылки на исходники закреплены за SHA и учитывают корень проекта. Для однозначно
найденных фрагментов добавляется номер строки. Рабочая ссылка на редактор отдельная.
Окружающие абзацы и заголовки дают контекст; повторяющиеся/неоднозначно найденные
фрагменты помечаются. `stale: true` означает, что ветки или PR/MR изменились после
проверки: для применения требуется новый анализ.

По явному запросу «подробный анализ конфликтов», «покажи изменения» или «diff»
используется `mode: "detailed"`: исходный фрагмент, обе версии и окружающий текст
показываются непосредственно. Следуйте `nextCursor` по файлам,
`nextFragmentCursor` по фрагментам и `nextReferenceCursor` по ссылкам на статьи.
Для последних двух укажите `path`. Обрезанные фрагменты имеют `truncated: true`.
`get_conflict_file` возвращает целую текстовую версию частями через `offset`,
`limit` и `nextOffset`, если для решения нужен полный контекст.

В обоих режимах изображения, GIF, видео и бинарные вложения проверяются только
по наличию и идентичности версий. Содержимое, превью, пиксели и кадры не передаются
агенту. Подробный анализ не разрешает просмотр медиа автоматически: нужен отдельный
явный запрос пользователя на конкретные файлы и версии, доступные по ссылкам отчёта.
Текстовый инструмент отклоняет запросы содержимого медиа.

Анализ Git сначала проверяет поддержку protocol v2 и `filter` без скачивания
объектов. Если выборочная загрузка недоступна, он завершается ошибкой до fetch,
а не скачивает репозиторий целиком. Статические ссылки на медиа ищутся в текстах
обоих снимков в пределах document roots, с ограничением количества и объёма
документов. Неполная проверка отмечается `referencesChecked: false`.
Динамические ссылки не выполняются; отсутствие найденных статических ссылок
не доказывает, что файл нигде не используется. Публикация решения выполняется
обычным Git и может потребовать загрузки объектов для проверки полного слияния;
они не передаются модели для визуального анализа.

`resolve_review_conflicts` требует `pushdocs:submit`, свежий `inspectionId`,
`idempotencyKey` и решение для каждого конфликтующего файла. `choice: "branch"`
или `"target"` выбирает соответствующую сторону всех конфликтных фрагментов
текста, сохраняя чистые правки из обеих веток. Для медиа и конфликта удаления
выбирается файл целиком, включая удаление. `choice: "combine"`
принимает все конфликтные фрагменты по `index` с выбором `branch`, `target`
или `manual` и своим `content`. Сервер собирает результат из оригинальных секций,
сохраняя чистые изменения вне конфликтов. Медиа допускают только выбор версии.
Анализ сам по себе изменений не применяет. Неоднозначные решения агент согласует
с редактором, однозначные применяет в пределах явного запроса на разрешение.

После неуспешной или неопределённой отправки подготовленное решение сохраняется.
Если `get_operation_status` сообщает `canResumeConflictResolution: true`,
`resume_conflict_resolution` с новым ключом продолжает то же задание, сохраняя
решения и подготовленный commit. При необходимости используется новый OAuth grant.
Уже опубликованный результат только сверяется и не отправляется повторно.
Отозванный grant считается постоянной ошибкой, а не причиной фоновых повторов.

Для rebase сначала вызывается `update_review_branch`. При `needs_resolution`
опрос останавливается: `operationId` используется как `inspectionId` в отчёте.
`inspect_review_conflicts` также возвращает текущий остановленный rebase, если он есть.
Отчёт содержит `comparisonKind=rebase`, номер коммита, его SHA, заголовок и `rebase.conflictId`.
Здесь `base` — родитель исходного коммита, `branch` — актуальная основа с уже
перенесёнными коммитами, `target` — переносимый исходный коммит. Для неопубликованной
основы внешние ссылки отсутствуют. Медиа проверяются только по метаданным.

В `resolve_review_conflicts` обязательно передаются точный `conflictId` из отчёта и
решения всех файлов. Продолжается то же задание: оно может снова перейти в
`needs_resolution` для следующего коммита. Решения предыдущего шага не переносятся
автоматически. Только после всех коммитов выполняется один push с точным lease.
Исходные SHA, политика и права повторно проверяются; изменение входов останавливает
операцию. В UI остановленный rebase можно отменить без изменения удалённой ветки.
Без активного rebase анализ сравнивает конечные версии веток и не запускает перенос.
Подмена rebase merge-решением запрещена; неподдерживаемые переименования и
структурные конфликты не публикуются через этот инструмент.

Приостановленное слияние также продолжает ту же операцию: отчёт содержит `merge.conflictId`, который нужно передать в `resolve_review_conflicts`. Обычные завершённые проверки конфликтов сохраняют прежний сценарий.

## Поиск и навигация

Topic search использует lexical ranking. Он может пропускать статьи, если запрос
и документ не содержат общих терминов. Literal search ищет также в исходнике
frontmatter и code blocks. Результаты разбиваются на страницы.

Backlinks учитывают рабочие документы. Динамические и неоднозначные MDX-ссылки
возвращаются как unresolved. Repository JavaScript при анализе не выполняется.

Navigation tools поддерживают static JS object/array literals, экспортированные
через `module.exports` или `export default`, в том числе через переменную.
Форматирование вне изменяемого literal сохраняется; сам literal форматируется
заново. Dynamic JS и TypeScript configs возвращают unsupported error.

Получите sidebar через `get_navigation`, используйте возвращённые item IDs и
ревизию. Position принимает число, `first`, `last`, `{before: itemId}` либо
`{after: itemId}`. Удаление записи из sidebar сохраняет документ.

## Орфография и изображения

Проверка работает локально через nspell и Hunspell dictionaries. Лицензии:
MIT для nspell, MIT/BSD для dictionary-en и BSD-3-Clause для dictionary-ru.
Добавьте продуктовые слова в versioned файл:

```json
{"ignoredWords": ["PushDocs", "Sendsay", "саблогин", "webhook"]}
```

Путь файла: `.pushdocs/spelling.json`. Проверка пропускает код, URLs, imports,
MDX syntax и технические identifiers. Диапазоны corrections относятся к
исходному документу и требуют проверки его ревизии.

Image tools сохраняют формат, проверяют исходный hash и не заменяют файл,
если размер не уменьшился. Поддерживаются статические JPEG, PNG, WebP, AVIF
и безопасные статические SVG. Анимация и смена формата не поддерживаются.
Изменение общего asset влияет на все использующие его статьи.

## Preview

Существующие endpoints preview публичны и не проверяют OAuth или browser session.
Оператор должен явно принять эту модель и установить:

```sh
PUSHDOCS_MCP_ALLOW_PUBLIC_PREVIEW=1
```

Без настройки `start_preview` возвращает `PREVIEW_ACCESS_POLICY`.
Для приватной документации сначала требуется защитить публикацию preview.

Agent lease действует 30 минут. `start_preview` с новым idempotency key продлевает
его. `get_preview_status` не продлевает lease. `stop_preview` освобождает только
lease текущего OAuth grant. Browser leases продолжают работать независимо.

Ответ содержит `appliedSha`, `appliedRevision` и `contentCurrent`. Готовность
процесса не гарантирует применение последней сохранённой правки.

`list_previews` возвращает данные раздела «Предпросмотр» для проекта, включая
очередь, основную ветку, статус, дату создания, длительность завершённого запуска
в миллисекундах и минутах, плановую дату удаления, размер в байтах, количество
неотправленных файлов, текущий этап и назначенный URL. Поддерживает `cursor` и
`limit`. Требует только `pushdocs:read` и не запускает сайты. Назначенный URL
сохраняется после остановки и не означает, что сайт работает.
`get_preview_status` также возвращает эти данные для ветки в поле `inventory`.

Поле `idleStopAt` показывает серверный срок автоматической остановки после выхода
из «Документов». Возврат в раздел отменяет этот срок; следующий выход задаёт новый
срок через один час. Активные вкладки поддерживают аренду. Явная остановка действует
сразу. Аренда MCP сохраняет отдельный срок 30 минут.

## Проверки

```sh
yarn test
yarn typecheck
yarn architecture:check
yarn build
```

Для интеграционного smoke test задайте `PUSHDOCS_TEST_DATABASE_URL` на отдельный
локальный PostgreSQL с правом создавать БД:

```sh
yarn test:mcp
```

Тест создаёт и удаляет случайную БД и использует настоящий MCP SDK client через
HTTP route. После `yarn build` можно также выполнить `PUSHDOCS_MCP_NETWORK_SMOKE=1 yarn test:mcp`: тест запустит standalone web application на временном HTTP-порту. Он не авторизуется в пользовательских accounts и не обращается
к production repositories. Ручная проверка обоих целевых клиентов остаётся
отдельным условием приёмки.

Браузерная проверка consent: `PUSHDOCS_MCP_BROWSER_SMOKE=1 yarn test:mcp`

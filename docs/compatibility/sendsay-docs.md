# Совместимость sendsay-docs с PushDocs

Дата проверки: 7 сентября 2026 года.

Проект можно поддержать в PushDocs без смены Docusaurus, React, Yarn и существующего GitLab CI. Для полноценной работы нужна версионируемая конфигурация репозитория и общие функции из [плана разработки](../development-plan.md). Отдельного адаптера sendsay-docs в коде сервиса не будет. Упоминания профиля ниже обозначают данные этой конфигурации, а не отдельный модуль для проекта. Первоначальный импорт `docs` и Markdown-редактор без правил Docusaurus для этого проекта недостаточны.

Требования внесены в [ADR-0001](../adr/0001-pushdocs-architecture.md). Сам сервис и его импортер пока не реализованы, поэтому вывод означает подтверждённую совместимость структуры и выбранного подхода с конкретными условиями реализации. Это не результат успешного end-to-end импорта в готовую CMS.

## Область и способ проверки

Исследован [репозиторий sendsay-docs](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs) с GitLab project ID `9`. Основной снимок, ветка `stable`, commit [`9a8fc074742f14befadb5ebf940ec4948d72f9d4`](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/commit/9a8fc074742f14befadb5ebf940ec4948d72f9d4). Данные веток, MR и jobs прочитаны через существующий авторизованный GitLab API. Исходные тексты получены через Git с частичной загрузкой объектов.

Проверены конфигурация сайта, lockfile, локальный docs-плагин, все 693 Markdown/MDX-файла в `docs` и `i18n`, метаданные категорий, исходники используемых компонентов и CI. Дополнительно прочитан `package.json` ветки `dhub`. Остальные ветки проверялись как метаданные, а не как полный корпус содержимого.

Разбор текста выполнен локально без запуска конфигурации, скриптов или React-компонентов репозитория. Использованы доступные зависимости `unified 11.0.5`, `remark-mdx 3.1.1`, `remark-gfm 4.0.1`, `remark-frontmatter`, `remark-directive`, `@slorber/remark-comment 1.0.0` и преобразования совместимости из `@docusaurus/mdx-loader 3.9.2`. Исходный проект использует Docusaurus 3.6.3, поэтому синтаксический эксперимент не является полной сборкой на его точных зависимостях.

Проверка не создавала коммитов, MR или комментариев и не запускала pipeline. Локальная копия исходников осталась без изменений. Полная сборка и визуальный round-trip в PushDocs не выполнялись. Бинарные вложения инвентаризированы по дереву Git, а не проверены декодированием каждого файла.

## Обнаружение контента и навигация

В [docusaurus.config.ts](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/docusaurus.config.ts) стандартный docs внутри classic preset отключён. В [plugins.ts](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/plugins.ts) подключён `src/plugins/docs-plugin-extended` с `routeBasePath: '/'` и `sidebars.js`.

[Обёртка плагина](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/src/plugins/docs-plugin-extended/index.js) вызывает обычный `@docusaurus/plugin-content-docs`, добавляет данные недавно обновлённых статей и затем вызывает исходный `contentLoaded`. Формат хранения документов остаётся стандартным. Для импорта достаточно явно описать обёртку в профиле, а выполнение её JavaScript внутри CMS не требуется.

[sidebars.js](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/sidebars.js) содержит `docs`, `integrations`, `videolessons` и `updates` с `autogenerated`, а также ручной `docs-en` с category shorthand. В файле литеральный объект, объявление переменной и `module.exports`; для известной структуры достаточно статического AST-адаптера.

Добавление английской статьи в файловое дерево без изменения `docs-en` не завершает сценарий публикации. В первоначальном ADR редактирование JS-навигации оставалось ограничением; для литерального формата sendsay-docs оно теперь входит в обязательную реализацию.

## Локализация и связанные файлы

Английский раздел имеет дополнительный слой маршрутизации. По [README](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/README.md) и проверенным исходникам перевод статьи включает настоящий текст, заглушку с ID, служебный файл на пути исходного документа, sidebar и реестр URL.

Например, перевод инструкции про SMS связан со следующими данными:

| Назначение | Файл или значение |
| --- | --- |
| Настоящий английский текст | `i18n/en/docusaurus-plugin-content-docs/current/en/other-channels/how-to-connect-sms.md` |
| ID и заглушка в исходном docs | `docs/en/other-channels/how-to-connect-sms.md`, `id: en-how-to-connect-sms`, `draft: true` |
| Служебный файл на полном исходном пути | `i18n/en/docusaurus-plugin-content-docs/current/other-channels/sms/how-to-connect-sms.mdx`, `draft: true` |
| Запись sidebar | `en/other-channels/en-how-to-connect-sms` в `docs-en` |
| Slug настоящего перевода | `/other-channels/sms/how-to-connect-sms` |
| Публичная английская ссылка | `/en/other-channels/sms/how-to-connect-sms` в `config/translatedLinks.json` |

Расширения служебного файла и настоящего перевода могут различаться. Простая замена префикса `docs/` на `i18n/en/.../current/` не описывает эту связь полностью.

[scripts/translate.mjs](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/scripts/translate.mjs) создаёт отсутствующие файлы по шаблону, проверяет совпадение расширений и при смене расширения переносит содержимое перед удалением старого файла. Скрипт не выполняет перевод текста. [redirectTemplate.md](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/config/templates/redirectTemplate.md) содержит импорт `Redirect` и переход на `/404`.

CMS должна показывать настоящие переводы отдельно от технических заглушек. Создание новой русской статьи включает служебный английский файл согласно профилю. Создание, перенос и удаление английской статьи обновляет весь связанный набор, включая `translatedLinks.json` и sidebar. Автоматическое удаление настоящего перевода при смене пути недопустимо.

Реестр `translatedLinks.json` используется [переключателем языка](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/src/theme/NavbarItem/LocaleDropdownNavbarItem/index.tsx). При отсутствии URL в реестре пользователь сайта отправляется на `/en/`, даже если файл перевода уже существует.

README содержит устаревшие примеры, поэтому профиль строится по коду. Например, текущий индекс обновлений находится в `docs/updates/list/index.mdx`, а не в упоминаемом в README `docs/updates/index.mdx`. Упомянутого `config/restrictedAccessRoutes.json` в проверенном дереве также нет; фактически присутствует `config/searchExcludeRoutes.json`.

## Проверка Markdown/MDX

Первый синтаксический проход обычным MDX-парсером успешно разобрал 681 из 693 файлов. Все 12 первоначальных ошибок встретились на HTML-комментариях. После подключения совместимости комментариев осталась одна ошибка на `### Действия с корзиной {#cart-actions}` в `docs/ecom/how-to-configure-data-transfer.md`.

После применения преобразований совместимости Docusaurus для комментариев, якорей и admonitions разобраны все 693 файла, без ошибок YAML front matter. Docusaurus документирует соответствующие настройки `mdx1Compat`; они включены по умолчанию. См. [руководство перехода на Docusaurus 3](https://docusaurus.io/docs/migration/v3).

В итоговом дереве обнаружены таблицы в 48 файлах, admonition/directive-блоки в 160 файлах и ссылки `pathname://` в 179 файлах. HTML entities, например `&nbsp;`, встречаются в обычном тексте; их нельзя терять при преобразованиях. Комментарии `<!-- prettier-ignore -->` влияют на существующее форматирование и должны сохраняться в исходнике.

Результат подтверждает возможность разобрать корпус с правильным диалектом. Он не доказывает, что MDXEditor уже умеет безопасно отредактировать и сериализовать каждую такую конструкцию. Критерий готовности включает побайтовое отсутствие изменений при no-op и отдельные проверки редактирования соседнего текста с сохранением комментариев, импортов, якорей и выражений.

[Индекс обновлений](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/docs/updates/list/index.mdx) импортирует два MDX-компонента и их `toc`, затем экспортирует объединённый массив. Это обязательный пример для сохранения ESM и зависимостей между документами. Добавление нового выпуска требует изменить индекс и добавить статью в одном наборе.

Front matter включает `recent_article` в 184 файлах, `sidebar_custom_props` в 31, а также `feedback_ignore`, `fullscreen`, `unlisted`, `custom_edit_url` и поля пагинации. В статьях обновлений используются отрицательные `sidebar_position`, например `-8`. Форма метаданных должна сохранять вложенные объекты, неизвестные поля и допустимые отрицательные значения.

`restrictedAccessHref` относится к поведению исходного сайта и его sidebar. Импортер не должен считать такое поле назначением роли PushDocs или подтверждением серверной защиты страницы. Права CMS проверяются независимо.

## Вложения и preview

[Конфигурация staticDirectories](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/docusaurus.config.ts) подключает общие `static` и локализованный каталог по `DOCUSAURUS_CURRENT_LOCALE`. Профиль должен различать путь на диске и публичный URL.

| Назначение | Каталог | Принятая форма URL |
| --- | --- | --- |
| Русские изображения | `staticLocalized/ru/img` | `/img/...`, включая `pathname:///img/...` |
| Английские изображения | `staticLocalized/en/img` | `/en/img/...` согласно соглашению проекта |
| Общие ресурсы | `static` | Путь зависит от ресурса и правил base URL |

Импортер сохраняет буквальную форму существующей ссылки. `pathname://` означает особое поведение Docusaurus и не является HTTP-протоколом скачивания. Лимиты новой загрузки в CMS не должны блокировать импорт уже существующих больших GIF или видео. Файлы не перекодируются и не перемещаются массово.

Проект уже собирает точный preview через CI. [.gitlab/preview-sites.json](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/.gitlab/preview-sites.json) задаёт сайт `docs`, Node 20.19.6, установку Yarn 1 и `yarn build`. Код [.gitlab/scripts/preview-utils.mjs](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/.gitlab/scripts/preview-utils.mjs) формирует URL вида `https://pr-<iid>.docs.sendsay.dev`, с возможностью переопределения через окружение.

Источник для CMS, артефакт `preview-metadata/preview-docs.json` из успешной `preview:deploy`. Его поля включают `preview_url`, `conclusion`, `logs_url` и время сборки. SHA берётся из job и pipeline. Артефакт хранится 7 дней, а URL preview изменяемый, поэтому однажды найденная ссылка не считается вечным подтверждением актуальной сборки.

Бот создаёт или обновляет общий комментарий с маркером `preview-deploy`. PushDocs должен отображать изменения такого комментария без дублирования. Сам текст комментария не заменяет проверку текущей job.

## CI, ветки и состояние слияния

[autofix.yml](https://gitlab.sndsy.ru/sendsay-ru/frontend/sendsay-docs/-/blob/9a8fc074742f14befadb5ebf940ec4948d72f9d4/.gitlab/ci/autofix.yml) выполняет `yarn fix`, создаёт коммит `autofix` при наличии изменений и отправляет его в source branch MR. `yarn fix` сначала синхронизирует служебные переводы, затем запускает форматирование. Следовательно, исходная ветка может измениться сразу после отправки из CMS.

PushDocs должен перечитать её head и обновить базу черновика без потери ввода. Если внешний коммит появился во время ручного разрешения конфликта или rebase, сохранённый план устаревает. Повтор операции не должен отменять изменения CI.

У проекта настроен fast-forward merge. Для сохранения выбранного workflow в профиль включён rebase исходной ветки на `stable`, с разрешением конфликтов в UI. Само `merge_method=ff` не доказывает запрета merge-коммитов во всей истории. Приложение не должно менять настройку слияния проекта или молча добавлять merge-коммиты для обхода необходимости обновить ветку. См. [GitLab merge methods](https://docs.gitlab.com/user/project/merge_requests/methods/).

При этом API сообщает `only_allow_merge_if_pipeline_succeeds=false` и `only_allow_merge_if_all_discussions_are_resolved=false`. PushDocs отображает реальные настройки. Успех CI и закрытые обсуждения нельзя объявить обязательными правилами провайдера, пока они там не настроены. Дополнительные ограничения CMS могут быть явно заданы администратором проекта.

| Поле профиля | Значение или правило |

## Работа нескольких проектов

Одна установка PushDocs должна одновременно обслуживать sendsay-docs и другие проекты. В ADR это закреплено как требование первой версии, с общей инфраструктурой и отдельным состоянием проектов.

Проект хранит собственные профиль импорта, repository ID, корень, ветки, каталог компонентов и правила вложений. Данные документа идентифицируются как минимум проектом, контекстом ветки и документом. Одинаковые пути и названия веток в разных проектах не конфликтуют.

Учётные записи общие для установки, а доступ и одна из трёх ролей назначаются отдельно в каждом проекте. Участие в sendsay-docs не даёт доступа к другим проектам. Оператор установки разрешает проекту конкретное подключение и репозиторий; общий Git-токен не расширяет права пользователя CMS.

Несколько проектов одного монорепозитория координируют запись одного ref, а общие конфиги и каталоги явно описываются в профилях. Один webhook может затронуть несколько проектов. Архивация одного проекта не удаляет чужие вложения, общий Git-кеш или используемое соседями подключение.
